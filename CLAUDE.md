# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Four co-existing subsystems, mostly **not integrated** with each other:

1. **AI-powered Loan Assessment Agent** (the active line of work) — an end-to-end pipeline that generates a synthetic applicant dataset, trains Logistic Regression and XGBoost credit-risk models on it (Logistic Regression is production — see "Current model status"), simulates mock salary-slip/bank-statement documents, extracts structured data back out of those documents, and scores an applicant via a CLI (`app.py`) that prints a Customer Risk Analysis Report.
2. **Original rules-based document pipeline** (`api/`, `ingestion/`, `extraction/extractor.py`, `validation/`, `scoring/`, `decisioning/`, `output/`, `pipeline.py`) — an earlier, self-contained FastAPI service that accepts uploaded loan documents and returns an Excel decision report using hand-written regex extraction and a DTI-based scoring formula. Still functional and tested, but a separate prototype — it does not call into the ML model or vice versa.
3. **`agentic_api/`** — a FastAPI service standing up an HTTP surface in front of the ML pipeline's document extraction + scoring layers (otherwise CLI-only via `app.py`). Extraction tries the regex parsers (`extraction/salary_slip_parser.py`, `bank_statement_parser.py`) first and falls back to the Gemini multimodal extraction agent (`extraction/gemini_extractor.py`) only when regex fails — see "Gemini extraction agent" below. Two endpoints: `/extraction/preview` (extraction-only preview of the recovered fields plus which method supplied them, no scoring) and `/scoring/assess` (extraction + the production risk model in one call, returns a Ledger-shaped record). `Applicant_ID` and `Applicant_Name` are caller-supplied form fields, not document-recovered — see `main.py`'s docstring above `ScoringResult` for why.
4. **`frontend/`** — a React + Vite + Zustand dashboard, gated behind a client-side-only `Login` screen (hardcoded `admin`/`admin@123` — a placeholder stopgap that only checks credentials in bundled JS, trivially bypassable via devtools, not real auth) and laid out as a persistent `Sidebar` (Dashboard/Ledger/Insights/Decision History/Pipeline nav, plus a standalone "New Application" button) + `Header` (system-status/pending-reviews pill) shell around a scrollable content area — this replaced the previous flat top-pill tab bar. Pages: Dashboard (portfolio-summary tiles + recent-submissions list, reading live from the store), Ledger, Insights, Pipeline (still illustrative/static — the one page not wired to real data), Upload, Pending Reviews, and Decision History (a filterable log of already-approved/rejected applicants). The Upload tab's extraction-preview and scoring steps call the real `agentic_api` endpoints (via a Vite dev-server proxy at `/api`, see `frontend/vite.config.js`) and push scored applicants into the Ledger; Insights and Dashboard both read from that same store. A HITL (human-in-the-loop) layer sits on top: **every** scored applicant now lands in "Pending Reviews" (`Review_Status: "pending"`) for an explicit Quick Approve / Manual Review / Reject decision, regardless of its risk verdict or consistency flag — those still drive the recommendation shown, just no longer an auto-decision (a deliberate policy change; see `useLoanStore.js`'s `deriveReviewStatus()`) — with the original uploaded documents retained in-browser as object URLs for the session, revoked on logout (which also drops the user back to the Login screen). Every approve/reject decision is appended to a local Excel log via `agentic_api/excel_manager.py`'s `/save-applicant` endpoint, called from the frontend via `frontend/src/lib/saveApplicant.js` (fire-and-forget — a failed export never blocks the review decision that triggered it). See "Where things stand" below.

### Rebuilding the ML pipeline from scratch (all steps are seeded/reproducible)

Run in order — each stage's output feeds the next:
```
python -m loan_processing.data_generation.applicant_generator      # -> data/raw/applicants.csv (10000 rows, seed=42)
python -m loan_processing.document_simulation.generate_mock_documents  # -> data/mock_documents/ (5 sampled applicants, seed=42)
python -m loan_processing.risk_modeling.train                      # -> data/processed/applicants_labeled.csv, models/*.pkl, reports/figures/*.png
python -m loan_processing.extraction.extract_applicant [Applicant_ID]  # demo: extract one applicant, print DataFrame + ground-truth cross-check
python app.py <Applicant_ID> <Date_Of_Birth YYYY-MM-DD>             # e.g. python app.py APP01732 1988-04-12 — full end-to-end report
```
All these outputs are already committed, so none of this needs to be re-run unless you want fresh data or the seeds change.

Run the original rules-based API: `uvicorn loan_processing.api.main:app --app-dir src --reload`

Run the extraction/scoring API: `uvicorn loan_processing.agentic_api.main:app --app-dir src --reload` (needs `GEMINI_API_KEY` in a `.env` file at repo root — copy `.env.example` — only for documents that fail regex extraction; regex-matching documents, including this project's own mock ones, work with no key at all)

## Architecture — AI Loan Assessment Agent

```
data_generation -> document_simulation -> risk_modeling (label + train) -> extraction -> app.py
```

- **`data_generation/`** (`schemas.py`, `applicant_generator.py`) — generates 1000 synthetic applicants with *correlated*, grounded numeric distributions (income drives EMI burden and bank balance; EMI burden and bounced transactions pull CIBIL score down) rather than independent random noise. `full_name`/`employer_name` are included beyond the originally-requested columns specifically so document_simulation has identity text to render.

  **`Requested_Tenure_Months` and `Requested_Loan_Amount` are generated together, tenure-first** (a fix, not the original design — see "Current model status"): tenure is drawn from a realistic real-world spread of common loan terms (12–240 months, weighted toward mid-length ones), then loan amount is *derived* from a target debt-service ratio (a right-skewed draw — most applicants target a serviceable EMI, a minority target a genuinely aggressive one) inverted against that tenure via the standard amortization formula (`risk_modeling/emi.py`) — the same "how much can I borrow at this EMI, over this term" calculation a real applicant/lender would do. Loan amount naturally scales with both income and tenure as a result (a longer tenure affords a bigger loan at the same monthly burden). The **previous** design sampled loan amount as a flat 1–6× multiple of annual income independently of tenure, which left roughly two-thirds of the synthetic population requesting a loan whose own EMI already exceeded their monthly income outright — nothing to do with real-world lending, and it made `Requested_EMI_to_Income_Ratio` below unable to separate genuinely risky requests from typical ones.

- **`risk_modeling/emi.py`** — a small shared module (only `numpy`, no other project dependency) housing `estimated_monthly_installment()` (standard reducing-balance EMI formula, vectorized, NaN-safe for missing/non-positive tenure) and `ASSUMED_ANNUAL_INTEREST_RATE` (a deliberate simplifying assumption — a representative Indian retail-loan rate — since neither the extraction pipeline nor the loan-application form captures a real, product-specific rate). Used identically by both `applicant_generator.py`/`labeling.py` (synthetic ground truth) and `train.py` (model feature), so the two can't drift apart. Lives in its own leaf module rather than being duplicated inline (the usual convention in this pair of files — see `labeling.py`'s docstring) because `labeling.py` cannot import from `train.py` (train.py already imports labeling.py; a reverse import would be circular).

- **`risk_modeling/labeling.py`** — the raw dataset has features but no ground-truth outcome, so this derives a synthetic `Default` target: a z-scored logistic combination of the same risk factors (CIBIL score, EMI burden, bounced transactions, loan-to-income, income level, deductions-to-gross, cash-flow trend, and the requested loan's own tenure-adjusted affordability via `emi.py`), with its intercept calibrated (binary search) to hit a target ~17% base rate, plus Gaussian noise so the label isn't perfectly separable from the features. This is what makes the classifier evaluation in `train.py` meaningful rather than trivial.

- **`risk_modeling/train.py`** — `FEATURE_COLUMNS` and `build_features()` here are the **single source of truth** for the model's expected input schema (14 features: `Employment_Type` — the one raw-categorical feature, `Salaried`/`Self-Employed`/`Business Owner` — `Is_First_Loan`, and five engineered ratios/derived features: `EMI_to_Income_Ratio`, `Loan_to_Annual_Income_Ratio`, `Deductions_to_Gross_Ratio`, `Cash_Flow_Trend_Slope`, `Requested_EMI_to_Income_Ratio`). `Gross_Income`, `Total_Deductions`, and the 6 raw `Cash_Flow_Month_1..6` columns are generated but, like `CIBIL_Score`, never handed to the model directly — only through their derived ratio/slope. **`CIBIL_Score` (a credit-bureau score) is deliberately excluded** — the model relies entirely on income/EMI/balance/repayment-behavior signals instead of a bureau pull; it's still generated as a synthetic applicant attribute (`data_generation/`) and still feeds the synthetic `Default` label in `labeling.py`, it's just never handed to the classifier as an input. `extraction/record_builder.py` imports `FEATURE_COLUMNS`/`build_features()` directly rather than re-deriving them, so extraction output can never drift out of sync with what the saved model actually expects.

  **`Requested_EMI_to_Income_Ratio`** (added — see "Current model status"): the *requested* loan's own estimated installment (`emi.py`, at the assumed rate) against income. Unlike `Loan_to_Annual_Income_Ratio`, this is tenure-sensitive — the same loan amount compressed into a short tenure produces a much higher ratio here than the identical amount spread over a long one, which a coarse loan/annual-income ratio can't distinguish on its own. This closed a real gap: a large loan requested over a short tenure (whose own EMI would badly exceed income) previously scored as low-risk, because neither the label nor any feature ever combined loan amount with tenure to check basic affordability — `Loan_to_Annual_Income_Ratio` ignores tenure, and `Requested_Tenure_Months` alone carries no income-affordability information. NaN wherever `Requested_Tenure_Months` is itself NaN (a caller-supplied loan-application-form field, optional at scoring time).

  **Preprocessing is a real `sklearn.compose.ColumnTransformer`, not hand-rolled columns** (was a manually-computed `Is_Self_Employed` 0/1 flag before `Employment_Type` gained a third category — see "Current model status" below): `_build_preprocessor()` one-hot encodes `Employment_Type` via `OneHotEncoder(handle_unknown="ignore", sparse_output=False)` — an unseen category at scoring time degrades gracefully (zero-filled dummies) instead of raising — and scales the numeric features (median-imputing them first for the Logistic Regression path only; XGBoost keeps true `NaN` via its own `missing=np.nan`). Trains Logistic Regression + XGBoost, applies **SMOTE only to the training split** (never the test set — that would leak; on the synthetic production dataset training now has no per-row missingness at all, since `CIBIL_Score` was the only field that ever had it — but the NaN-aware SMOTE path is retained because rows with any missing value, or, on a secondary dataset, whole columns missing for every row, are excluded from SMOTE's oversampling and kept unresampled instead, since it can't interpolate a genuinely-absent feature; SMOTE runs on the already-preprocessed array, since it can't interpolate a raw categorical string), evaluates with precision/recall/F1/AUC, and saves each model as **one bundled `sklearn.pipeline.Pipeline`** (`models/logistic_regression_pipeline.pkl`, `models/xgboost_pipeline.pkl` — preprocessor + classifier together, assembled from already-fitted pieces so SMOTE's bespoke logic didn't need to move inside an `imblearn.pipeline.Pipeline`) plus `models/feature_columns.pkl` (the raw pre-transform input contract). This replaced the previous 6-separate-artifact structure (`*_model.pkl` + `*_scaler.pkl` + `*_medians.pkl` per model) — scoring collapsed from a manual `fillna → scaler.transform → model.predict_proba` sequence to one `pipeline.predict_proba(raw_df)` call in both `agentic_api/main.py` and `app.py`.

  `main()` takes four optional overrides, all defaulting to the original synthetic/production behavior: `data_path` (train on a different CSV — see secondary-dataset section below), `exclude_features` (drop column(s) from *this run's* feature set only, without touching the shared `FEATURE_COLUMNS` contract `record_builder.py` depends on), and `models_dir`/`figures_dir` (save artifacts somewhere other than `models/`/`reports/figures/`, so an experimental run can never silently overwrite the production model). Exposed as `--data-path`, `--exclude-features`, `--models-dir`, `--figures-dir` on the CLI.

- **`document_simulation/`** (`salary_slip_pdf.py`, `bank_statement_xlsx.py`) — renders mock documents from a sampled applicant row. The bank statement simulator solves for the account's opening balance so the statement's **day-weighted** average balance (not a naive per-row mean, which over-weights the elevated post-salary-credit period) lands exactly on the applicant's stored `Average_Monthly_Bank_Balance`. Self-Employed applicants get "INCOME STATEMENT"/"BUSINESS INCOME" wording instead of "SALARY SLIP"/"SALARY".

- **`extraction/`** — `salary_slip_parser.py` (pdfplumber + regex) and `bank_statement_parser.py` (pandas; recomputes the same day-weighted average independently and cross-checks it against the statement's own stated header value as a verification step — this genuinely validates extraction fidelity, it isn't just reading the header). `record_builder.py` combines both and builds a model-input DataFrame via `risk_modeling.train.build_features`. Each parser is anchored to a **small, fixed set of known label vocabularies/layouts**, not a general-purpose parser: `salary_slip_pdf.py`'s own exact labels (`Employee Name:`, `Net Pay: Rs. ...`) plus, case-insensitively, a second vocabulary seen on a real-world test document (`EMPLOYEE NAME:`, `NET PAY:`/`GROSS INCOME:`/`TOTAL DEDUCTIONS:`, no currency prefix required) for the salary slip; the mock multi-column `"Statement"`-sheet layout plus a second, pipe-delimited-single-column layout (any sheet name, `WITHDRAWAL`/`DEPOSIT` instead of `Debit`/`Credit`, EMI rows matched by an `"emi"` substring rather than one exact description string) for the bank statement. A document using label text outside both vocabularies is still expected to fall through to Gemini — broadening regex is for *observed* format variants, not an attempt to make it a general-purpose parser.

  **Known gap, by design, not oversight**: a salary slip + bank statement can directly supply 8 of the model's 14 features non-`NaN` (`Age` and `Employment_Type` are caller-supplied rather than document-recovered, but non-`NaN` once supplied) — `Loan_to_Annual_Income_Ratio` and `Requested_EMI_to_Income_Ratio` still end up `NaN` since both depend on `Requested_Loan_Amount`/`Requested_Tenure_Months`. `Is_First_Loan`, `Requested_Loan_Amount`, `Requested_Tenure_Months`, and `Number_of_Bounced_Transactions_Last_6M` come back as explicit `NaN` (`FIELDS_NOT_AVAILABLE_FROM_THESE_DOCUMENTS` in `record_builder.py`) rather than fabricated defaults. `Applicant_ID`, `Age`, and `Employment_Type` are likewise never extracted — all three are required parameters the caller supplies: `Applicant_ID` because a real-world document has no machine-readable one, `Age` because `calculate_age()` derives it from a caller-supplied date of birth as of today rather than trusting a printed figure that goes stale, and `Employment_Type` because a self-reported document label isn't a reliable substitute for what the applicant actually selects on a loan-application form — and a document can't offer a category ("Business Owner") beyond whatever happens to be printed on it (see "Current model status" below for why this moved off the extraction layer entirely). `build_applicant_record()` also takes an optional `is_first_loan` override standing in for the (not-yet-built) loan-application-form extractor. Closing the rest of the gap needs bounced-transaction line items added to the mock bank statement generator (there's no `CIBIL_Score`/credit-bureau gap to close — the model doesn't use one).

  **`gemini_extractor.py`** — a fallback extraction strategy for the same document-derivable fields (minus `Applicant_ID`/`Age`, which are caller-supplied for both extraction paths - see above), using Gemini's multimodal document understanding instead of regex, via the current `google-genai` SDK (migrated off the EOL'd `google-generativeai` SDK). Two-tier model fallback: tries `gemini-pro-latest` (the user's originally-requested `gemini-1.5-pro` is fully retired — a hard 404, confirmed via `ListModels`) first, and on a 429/`RESOURCE_EXHAUSTED`/quota-shaped error specifically, logs a console warning and automatically retries once against `gemini-flash-latest` with the identical prompt/schema/documents — non-quota errors (auth failures, etc.) are not retried, since a different model tier wouldn't fix those. The returned dict carries `model_used`/`fallback_triggered` so callers (and the frontend's extraction-preview badge) can tell which tier served the request; `ScoringResult` exposes the same as `Model_Used`/`Fallback_Triggered`. Reads the salary slip PDF/image natively; the bank statement is rendered to CSV text first since Gemini can't parse raw `.xlsx` binary (a PDF bank statement is attached as binary, same as the salary slip). Output is constrained via Pydantic `response_schema` + `response_mime_type="application/json"`, not prompt instructions alone. `Cash_Flow_Trend` is recoverable two ways: read directly if the document states an explicit 6-month summary (this project's own mock statements), or computed by Gemini itself as day-weighted monthly averages from a raw dated-transaction-with-running-balance table when no such summary exists (verified against a real-world-style 6-month statement — Gemini's computed values matched an independent Python calculation to the cent) — only `null` if the document has fewer than 6 full calendar months of dated data to compute from at all. Needs `GEMINI_API_KEY`; an optional `GEMINI_API_KEY_SECONDARY` is consulted only as a last-resort escape hatch — if quota/rate-limit errors exhaust *both* model tiers on the primary key, the same Pro→Flash sequence is retried once more on the secondary key before giving up (added after hitting the free tier's 20-requests/day cap during testing). `extract_with_gemini_safe()` never raises, returning a null-filled dict + `_error` key on any failure (missing key, rate limit, timeout, schema violation) instead. Every Gemini call is capped by an explicit `http_options=types.HttpOptions(timeout=45000)` (milliseconds) — a prior deployment saw a single request hang for 5+ minutes with no visible error (consistent with the deprecated SDK's internal retry/backoff running silently), so this bounds the worst case rather than leaving a stuck request to block the caller indefinitely. `agentic_api/main.py`'s `_extract_financial_fields()` tries regex first and only calls this module when regex raises or the upload isn't a format regex can handle at all (a photographed salary slip, a PDF bank statement) — Gemini is never on the critical path for documents that already match this project's own mock format.

- **`app.py`** (repo root, not under `src/`) — the CLI entry point. Loads the **Logistic Regression** model + its own scaler + its own training medians (`logistic_regression_model.pkl` / `logistic_regression_scaler.pkl` / `logistic_regression_medians.pkl`), scores the extracted (partially-`NaN`) feature vector, and prints a report (5 sections for a first-time/NTC applicant, 4 otherwise). Logistic Regression, unlike XGBoost, can't accept `NaN` at all, so `score_applicant()` imputes any missing feature with its training-set median (persisted by `train.py`) before scaling and predicting — this is a real behavior difference from the previous XGBoost-in-production setup, which routed missing values via learned split directions instead of imputing. It does **not** weaken the report's honesty about missing data, though: **deliberate business-rule override** — if any required-but-missing field is absent, the Processing Recommendation is always "FLAG FOR MANUAL REVIEW" regardless of what the model predicts, because a real underwriting system shouldn't auto-approve on an incomplete picture; that check reads the record directly; it doesn't care what the model did internally. Accepts an optional `--first-loan {yes,no}` flag standing in for the application-form input; when `yes`, the report adds an NTC section noting the model doesn't use a bureau score for *any* applicant, so a first-time borrower isn't weighted differently on that front — the section flags instead that they have no repayment track record behind the alternative-data signals (`Monthly_Net_Income`, `Average_Monthly_Bank_Balance`) the assessment already rests on.

## Secondary-dataset benchmarking (`src/prepare_secondary_data.py`)

Maps a real Kaggle dataset onto the training schema above, as an academic-benchmark comparison against the synthetic data — kept entirely separate from the production pipeline (see "Current model status" below for what's actually loaded where).

- **Input**: `data/raw_kaggle_credit_data.csv` — the well-known Kaggle "Credit Risk Dataset" (`person_age`, `person_income`, `loan_amnt`, `loan_percent_income`, `loan_status`, `cb_person_default_on_file`, `cb_person_cred_hist_length`, ...). **Not committed** (large downloaded file, currently untracked) — place it there yourself to rerun this.
- **Real, structural gap, not a bug**: this dataset has no bureau-score column, no bank-transaction data, and no employment-type category at all. `CIBIL_Score` (moot either way now that it's not a model feature — see "Current model status" below), `Average_Monthly_Bank_Balance`, `Number_of_Bounced_Transactions_Last_6M`, and `Requested_Tenure_Months` come back `NaN` for every single row (not just NTC ones); `Employment_Type` is defaulted to `"Salaried"` for everyone. Only `Applicant_ID` (synthesized), `Age`, `Monthly_Net_Income`, `Requested_Loan_Amount`, and `Is_First_Loan` (from `cb_person_cred_hist_length == 0` — 0% of real rows meet this, so it's a genuine finding, not a script bug) carry real signal. `loan_status` is carried through unchanged as `Default` — a real label, so `train.py` skips `labeling.py`'s synthetic-label generation whenever a `Default` column is already present.
- **`inject_synthetic_cibil_score()`** (`--synthetic-cibil` flag) — deliberately **fabricates** a `CIBIL_Score`/`Is_First_Loan` pattern (drawn independently of the real outcome) for a controlled ablation ("does a populated-but-uninformative feature change model behavior"). Writes to a distinctly-named `data/final_training_data_synthetic_cibil.csv`, never the real mapping's output file, specifically so a fabricated run can never be mistaken for a real-data benchmark result.
- Both outputs feed `risk_modeling/train.py --data-path <file>`.

### Current model status

`CIBIL_Score` was removed from `FEATURE_COLUMNS` (design choice, not a gap — see `risk_modeling/train.py` above) and **Logistic Regression replaced XGBoost as the production model** (`app.py` loads it). `Gross_Income`/`Total_Deductions` and a 6-month cash-flow trend were added end-to-end, bringing the schema to 13 features. The synthetic dataset was then scaled from 1,000 → 10,000 rows (same generator, same `seed=42`). `Employment_Type` moved from document extraction to a required loan-application-form field, gaining a third category ("Business Owner") — added to the synthetic generator too (its own correlated income/volatility profile, not just a UI-only option), and the model's categorical encoding switched from a hand-rolled `Is_Self_Employed` 0/1 column to a real `ColumnTransformer` + `OneHotEncoder(handle_unknown="ignore")`, bundled into one `sklearn.pipeline.Pipeline` per model.

**Most recently: fixed a real scoring blind spot** — a large loan requested over a short tenure (whose own EMI would badly exceed the applicant's income) was scoring as low-risk, because nothing in the feature set or the synthetic label ever checked basic loan affordability (loan amount × tenure × income together). Root-caused to two compounding issues: (1) `FEATURE_COLUMNS` had no tenure-adjusted affordability signal — `Loan_to_Annual_Income_Ratio` ignores tenure entirely, and `Requested_Tenure_Months` alone carries no income-affordability information; (2) the synthetic generator drew `Requested_Loan_Amount` (a flat 1–6× multiple of annual income) and `Requested_Tenure_Months` *independently*, which meant ~65% of the synthetic training population already had a proposed EMI exceeding their entire monthly income — so this pattern looked normal, not risky, to anything trained on it. Fixed both: added `Requested_EMI_to_Income_Ratio` to `FEATURE_COLUMNS`/the label formula (see above), and redesigned `applicant_generator.py` to derive loan amount from a target debt-service ratio inverted against an independently-drawn realistic tenure (`risk_modeling/emi.py`) — dropping the unaffordable-EMI share of the population from ~65% to ~4.4%, a right-skewed minority matching real-world reckless-borrowing behavior rather than the typical case. Confirmed against a real reported case: a ₹90L loan against ₹1.35L/month income over 36 months (proposed EMI ≈ 2.18× monthly income) went from **1.2%** predicted default probability (verdict: low risk) to **99.4%** (verdict: high risk) after this fix, while a genuinely affordable request (₹8L over 60 months against the same income) still correctly scores at 0.1%. **Reading run #1 vs #2**: both AUCs improved slightly (LR +0.48pt, XGB +0.51pt) purely from giving the model a real third category to learn from — `Business Owner` applicants (their own distinct, higher-risk synthetic profile) were previously invisible to the binary `Is_Self_Employed` encoding, collapsed into whichever of the two existing buckets `== "Self-Employed"` happened to evaluate to. **Key findings:**
- **Loan affordability (tenure × amount × income) was invisible to the model until run #0** — see "Current model status" above. The biggest AUC jump in this table after the row-count scale-up came from a feature, not a bigger dataset.
- **Business Owner is a real, learned signal, not cosmetic** (see "Reading run #1 vs #2" above) — the model prices it distinctly higher-risk once it exists in training data.
- Scaling synthetic data 1,000 → 10,000 rows lifted both models' AUC (LR +3.4pts, XGB +3.8pts) and nearly closed the LR/XGBoost gap — driven by a far more reliable evaluation split (~352 default cases in test vs. ~34 before).
- **Model ranking flips between clean and real-world data.** Logistic Regression wins on synthetic data (no missing values). XGBoost wins on real Kaggle data (0.827 vs 0.765), because 6 of 13 features are always missing there and XGBoost natively routes around `NaN` while Logistic Regression must median-impute, destroying signal.
- **Seed variance is real at small `n`.** Same generator, same schema, only the seed changed (42→7) — AUC swung 6-7 points (run #3 vs #5). This directly motivated the 10,000-row scale-up (run #2, later superseded by #1).
- `CIBIL_Score` never helped on Kaggle data regardless of treatment — present as `NaN` (0.828) or fabricated (0.801), both close to the no-CIBIL number (0.826/0.827) — supporting the decision to exclude it from the model everywhere.

**Methodology (for an appendix/footnote slide):**
- Runs #1/#2/#3 — `python -m loan_processing.data_generation.applicant_generator` (seed as noted) → `python -m loan_processing.risk_modeling.train` (production paths); #1 additionally reflects the `Employment_Type` 3-category + `ColumnTransformer`/`Pipeline` change.
- Run #4 — `python src/prepare_secondary_data.py` (maps `data/raw_kaggle_credit_data.csv` → `data/final_training_data.csv`) → `train.py --data-path data/final_training_data.csv --models-dir models/experiments/kaggle_benchmark`.
- Run #5 — same generator at `seed=7` → `data/raw/applicants_synthetic_v2.csv` → `train.py --data-path ... --models-dir models/experiments/synthetic_v2`.
- Runs #6-8 — earlier ablations (see repo history / conversation record); #6 predates the current 13-feature schema, #7-8 were never saved under their own `models/experiments/` directory.
- All experimental runs used `--models-dir`/`--figures-dir` so production artifacts were never overwritten.

### Live-scenario recall benchmark

The table above only ever reports metrics against a clean, feature-complete synthetic test set — which turned out to hide a real problem: `Number_of_Bounced_Transactions_Last_6M` was permanently `NaN` for every single live-scored applicant (the mock bank statement never rendered bounce line items at all), and recall on the exact same held-out test rows crashed from **0.91 to 0.73** (further to **0.54** if `Requested_Tenure_Months` was also missing) despite the clean number staying a reassuring 0.9490 AUC throughout. Worse, since `Number_of_Bounced_Transactions_Last_6M` was on `record_builder.FIELDS_NOT_AVAILABLE_FROM_THESE_DOCUMENTS`, `agentic_api/main.py`'s `Consistency_Flag` was `False` for every applicant too — `frontend/src/store/useLoanStore.js`'s `deriveReviewStatus()` sent *every* applicant to Pending Review regardless of the model's prediction, silently defeating the auto-approve path entirely.

**Fixed** (see `document_simulation/bank_statement_xlsx.py`, `extraction/bank_statement_parser.py`, `extraction/record_builder.py`, `agentic_api/main.py`): bounced transactions are now rendered as real "CHEQUE BOUNCE CHARGE" debit rows and counted back out by the parser; `Requested_Tenure_Months` is now a genuinely required field (backend `Form(...)`, frontend `<select>` with no silent default); `Cash_Flow_Trend` now falls back to being computed directly from the parsed transaction table (`_day_weighted_monthly_averages`, same day-weighting `bank_statement_xlsx.py` uses to calibrate its own header) instead of only trusting a header field that only this project's own mock documents ever populate.

`risk_modeling/evaluate_live_scenario.py` is the standing benchmark this incident motivated: it re-evaluates the production pipeline against the *same* held-out test split `train.py` uses, both clean and with `Cash_Flow_Trend_Slope` forced `NaN` — the one remaining realistic gap (a bank statement with under 6 months of history is a real-world case no extraction-logic fix can manufacture data for). Post-fix result:

| Scenario | Accuracy | Precision | Recall | F1 | AUC |
|---|---|---|---|---|---|
| Clean (held-out test set) | 0.8785 | 0.5973 | 0.9072 | 0.7204 | 0.9490 |
| Live (`Cash_Flow_Trend_Slope` NaN) | 0.8790 | 0.6008 | 0.8899 | 0.7173 | 0.9465 |

Recall drop is now 0.017, not 0.18 — Tier 1 closed the real gap. `tests/unit/test_evaluate_live_scenario.py` guards this going forward (recall floor 0.80, clean-vs-live gap ceiling 0.15) so a future change silently reopening a permanent feature-availability gap gets caught by the test suite instead of only showing up as an unreported production regression. The classification threshold (`agentic_api/main.py`'s `classification_verdict = 1 if probability_of_default >= 0.5 else 0`) was reviewed against this and kept at 0.5 — the pre-fix crash was the actual problem, not the threshold itself.

**Known gotcha**: regenerating `applicants.csv` at a different `n` (even the same seed) does **not** preserve prior rows — several fields use rejection-sampling distributions (`rng.beta`, `rng.poisson`) that aren't prefix-stable across array sizes. Confirmed empirically when scaling to 10,000 rows: every field but `Applicant_ID` changed for the original first 1,000 rows. The 5 mock documents under `data/mock_documents/` were regenerated to match (old ones `git rm`'d, new sample: APP01732/APP04522/APP04685/APP04743/APP06253) — re-running the generator does not self-clean, so remember to remove stale IDs' files if `n` changes again.

**Gotcha for future runs**: `train.py`'s `LABELED_DATA_PATH` (`data/processed/applicants_labeled.csv`) is a hardcoded module-level constant, unlike `models_dir`/`figures_dir` — it is **not** parameterized by any CLI flag, so *every* `--data-path` run (Kaggle or a second synthetic dataset alike) overwrites this shared file with that run's own labeled rows, regardless of `--models-dir`. After running any benchmark, re-run `python -m loan_processing.risk_modeling.train` with no flags to restore it before trusting its contents as "production's labeled data" again (already done as part of producing the table above).

**Do not use `models/experiments/*` results as if they were the production model's numbers, and do not report the fabricated-CIBIL run's metrics as reflecting real secondary-dataset performance** — it was an explicit, labeled ablation on invented values, not a finding about CIBIL scores.

### Testing conventions

- `tests/unit/` covers each stage in isolation (data generation reproducibility/ranges, labeling calibration, document rendering round-trips, extraction fidelity, `app.py`'s report/recommendation logic, `gemini_extractor.py`'s schema validation/timeout-wiring/error handling via a mocked SDK — no real API key needed to run the suite) — no dependency on files under `data/` actually existing on disk; fixtures build everything in `tmp_path`.
- `test_prepare_secondary_data.py` verifies `prepare_secondary_data.py`'s mapping/NTC-engineering/cleaning/synthetic-CIBIL-injection logic against a small hand-built fixture matching the *assumed* Kaggle schema — it does not depend on the real (uncommitted) `raw_kaggle_credit_data.csv` and proves nothing about real-world numbers, only that the script's own logic is correct. `pyproject.toml` sets `pythonpath = ["src"]` so this loose top-level script (not part of the `loan_processing` package) is importable in tests.
- `tests/integration/test_api.py` drives the original FastAPI app with `TestClient`; `tests/integration/test_agentic_api.py` drives the new one the same way, using the real committed mock documents, exercising the regex success path plus the regex-fails-so-Gemini-gets-attempted fallback path (via Gemini's deterministic no-API-key failure, so no network call) on both `/extraction/preview` and `/scoring/assess`.
- The original rules-based pipeline's tests (`test_scoring.py`, `test_validation.py`, `test_output.py`) are unrelated to the ML pipeline's tests.

## Where things stand

All five phases are built, tested, and executed end-to-end: synthetic data (10000 applicants as of the latest scale-up, including ~15% new-to-credit — `CIBIL_Score` is still generated for these rows and still genuinely `NaN` for NTC ones, it's just no longer handed to the model as a feature for *any* applicant) -> labeled dataset -> trained Logistic Regression + XGBoost models + diagnostic plots -> 5 mock document sets -> `app.py` producing full reports for multiple applicants, with a dedicated NTC section when applicable. **`app.py` currently loads the Logistic Regression model, with `CIBIL_Score` excluded from its feature set and `Requested_EMI_to_Income_Ratio` included (AUC 0.9490) — see "Current model status" above before assuming any other model/number is what's loaded.** The 5 mock document sets under `data/mock_documents/` (APP01732/APP04522/APP04685/APP04743/APP06253) are back in sync with the current `data/raw/applicants.csv` as of the affordability-fix regeneration — see "Current model status" above for the reproducibility gotcha to watch for if `n` or the RNG draw sequence ever changes again. Everything from the original five phases is committed, including generated artifacts (`data/`, `models/`, `reports/figures/`) — regeneration commands above are for if you want fresh/different data, not required to pick the project back up. The secondary-dataset files (`data/raw_kaggle_credit_data.csv`, `data/final_training_data*.csv`, `models/experiments/`) are **not** committed as of this writing.

The `frontend/` (React + Vite + Zustand) dashboard is a fourth subsystem layered on top of the three above, sitting behind a client-side-only `Login` gate (hardcoded credentials, a placeholder stopgap — see item 4 above) and a `Sidebar` + `Header` shell that replaced the earlier top-pill tab bar. The Upload tab is wired to `agentic_api`'s real `/extraction/preview` and `/scoring/assess` endpoints (via a Vite dev-server proxy at `/api`) and pushes scored applicants into the Zustand store (`frontend/src/store/useLoanStore.js`), which the Ledger, Insights, Dashboard, and Decision History tabs all read from directly — that store still seeds nothing on its own (it starts empty; every row in it came from a real Upload submission this session). A HITL layer (Pending Reviews tab, Manual Review drawer, `agentic_api/excel_manager.py`'s `/save-applicant` endpoint) sits on top of that — **every** scored applicant now routes through it for an explicit human decision, not just applicants whose checks failed (auto-approve was removed; see item 4 above). The Pipeline tab is the one page still illustrative/static, not reading from the store.
